# BIUM — Digital Diet

> LLM 시대, 쌓이기만 하는 디지털 데이터를  
> **내 기기가 하나의 ‘작은 집’이 되고, 고양이가 방을 돌아다니며 찾아주는** 정리 경험으로 바꿉니다.

이 문서는 **발표용 피피티 개요서**입니다.  
슬라이드 순서 · 문제 정의 · 페인포인트 · 해결 · 기대효과를 한 흐름으로 정리합니다.

---

## 0. 피피티 한 장 요약 (Core Narrative)

```
LLM·생성형 AI로 데이터·클라우드 비용↑ · 환경 부담↑
        ↓
유저는 “어디에 뭐가 있는지 / 뭐가 중복인지 / 뭘 지워도 되는지” 모름
        ↓
가운데: USER PAIN (저장·분산·중복·삭제 불안·귀찮음·비용)
        ↓
BIUM (Digital Diet) = 디지털 집을 통합 탐색 → 근거 제시 → 사용자가 결정
        ↓
공간 확보 · 요금제 부담 완화 · 불필요 복제 감소 · 정리 습관화
```

## 1. 문제 제기 — 왜 지금인가

### 1-1. LLM이 데이터·클라우드 비용을 밀어 올린다

| 변화 | 결과 |
|------|------|
| 생성형 AI로 문서·이미지·영상·코드 산출량 급증 | 저장·백업·버전 히스토리 폭증 |
| 멀티모달·에이전트 워크플로 | 중간 산출물·캐시·로그가 조용히 쌓임 |
| SaaS·클라우드 기본값 = “일단 동기화·보관” | 사용자는 용량이 찬 뒤에야 인지 |
| 개인도 Drive / OneDrive / 메일 첨부를 일상 사용 | **방치 데이터 = 구독료 + 인프라 부하** |

핵심 메시지:

> “AI가 만들어 주는 결과물만큼,  
> **안 지워진 사본·버전·첨부가 클라우드를 먹고 있다.**”

### 1-2. 클라우드 유지에는 돈이 든다

소비자 클라우드(예시, 지역·프로모션에 따라 변동):

| 요금제 예시 | 대략 월 비용 | 연간 환산 |
|-------------|--------------|-----------|
| Google One 100GB | ~₩2,400대 | ~₩29,000 |
| Google One / iCloud 등 200GB~2TB | ~₩3,000–₩12,000+ | ~₩36,000–₩140,000+ |
| Microsoft 365 (OneDrive 포함) | 구독에 묶임 | 용량 초과 시 업셀 압력 |

**피피티용 한 줄:**

> 정리를 미루면 선택지는 둘뿐이다.  
> **① 계속 돈 내고 용량을 올리거나**  
> **② 어디를 지울지 모르는 채로 불안해하거나.**

> ※ 금액은 발표 시점 공개 요금제 기준의 **예시**이며, 제품 UI의 절감액은 mock/추정임을 명시한다.

### 1-3. 환경에도 영향을 미친다 (근거는 ‘범위 추정’)

클라우드 저장은 “공짜 공간”이 아니다.  
데이터센터 전력·냉각·복제(redundancy)가 계속 돌아간다.

참고용 추정 범위 (연구·계산기마다 편차 큼):

| 출처 성격 | 대략적 스케일 |
|-----------|----------------|
| Greenly 등 공개 추정치 | 미국 그리드 가정 시 **약 0.04 kgCO₂e / GB·년** 수준 언급 ([Greenly](https://greenly.earth/en-us/blog/industries/what-is-the-carbon-footprint-of-data-storage)) |
| Cloud Carbon Footprint 계열 | TB·년당 kWh는 매체(HDD/SSD)·복제·PUE·지역 전력에 따라 **수 배~수십 배** 차이 ([GreenCalculus 요약](https://greencalculus.com/calculators/cloud-storage-carbon-calculator/)) |
| Tech Carbon Standard | 주요 클라우드에 **1TB·년 ≈ 약 32 kWh** 수준 언급 사례 ([Tech Carbon Standard](https://www.techcarbonstandard.org/technology-categories/data)) |

**피피티 주의문구 (필수):**

> 탄소·전력 수치는 **검증된 개인별 실측이 아니라 공개 추정치의 오더(order of magnitude)** 이다.  
> 제품 화면에서는 확정 CO₂를 단정 표기하지 않고, 발표에서는 “방치 데이터가 인프라·에너지 부하를 남긴다”는 **방향성**으로 말한다.

## 2. 시나리오 슬라이드 — 유저 1명이 1년간 데이터를 방치하면

### 가정 (발표용 시나리오)

| 항목 | 가정값 | 설명 |
|------|--------|------|
| 방치·중복·오래된 후보 | **50GB** | Drive+메일+로컬 사본을 합친 ‘정리 가능’ 규모 |
| 기간 | **1년** | 삭제하지 않고 클라우드에 유지 |
| 비용 | 요금제 경계에 걸리면 | 무료→유료, 또는 상위 티어 압박 |
| 환경 | 추정 계수 사용 시 | 아래 환산표 |

### 발표용 환산 예시 (오더 오브 매그니튜드)

Greenly가 언급한 **~0.04 kgCO₂e / GB·년**을 **시나리오용 계수**로 쓸 때:

| 방치량 | 1년 추정 CO₂e | 감각 비유 (대략) |
|--------|----------------|------------------|
| 10GB | ~0.4 kg | 매우 작지만 “0은 아님” |
| 50GB | ~2 kg | 짧은 거리 이동·소형 소비에 비유 가능(비유는 지역·계수에 민감) |
| 100GB | ~4 kg | 방치가 쌓일수록 선형에 가깝게 증가 |
| 1TB | ~40 kg | 개인 스토리지 규모에서도 무시하기 어려운 상단 |

**피피티 카피:**

> 유저 한 명이 1년 동안 **50GB를 아무도 안 보는 채 클라우드에 두면**,  
> 그 데이터는 계속 **요금제 압력**을 만들고,  
> 데이터센터 관점에서는 **작지만 누적되는 에너지 부하**를 남긴다.  
> 문제는 “50GB가 무섭다”가 아니라  
> **전 세계 수억 명의 방치 사본이 동시에 쌓인다**는 점이다.

## 4. 페인포인트 전체 맵 (발표·리서치 공통 표)

대분류별로 **사용자 페인포인트 → 실제 표현 → 우리 서비스가 볼 데이터**를 대응한다.

### ① 무엇이 용량을 차지하는지 모름

| 사용자 페인포인트 | 실제 사용자 표현에서 확인할 내용 | 우리 서비스가 볼 데이터 |
|-------------------|----------------------------------|-------------------------|
| 저장공간이 왜 찼는지 모르겠다 | “분명 파일이 별로 없는데 꽉 찼다” | 저장소별 점유량 |
| 숨겨진 데이터가 용량을 차지한다 | 버전 기록 등이 예상보다 큰 공간 차지 | 버전·백업 데이터 |
| 어떤 파일부터 봐야 할지 모르겠다 | 대용량 원인 탐색 어려움 | 용량 순위 |

### ② 데이터가 여러 곳에 흩어짐

| 사용자 페인포인트 | 실제 사용자 표현에서 확인할 내용 | 우리 서비스가 볼 데이터 |
|-------------------|----------------------------------|-------------------------|
| PC와 클라우드 양쪽에 파일이 있다 | 로컬/클라우드 구조 혼란 | 파일 위치 |
| 여러 기기에서 같은 파일을 관리하기 어렵다 | 노트북·데스크톱 간 동기화 문제 | 기기간 파일 해시 |
| 어느 파일이 원본인지 모르겠다 | 사본·동기화본 구별 어려움 | 위치·수정일·해시 |
| 저장 위치를 기억하기 어렵다 | 여러 저장공간을 직접 탐색 | 통합 인덱스 |

### ③ 의도하지 않은 데이터가 쌓임

| 사용자 페인포인트 | 실제 사용자 표현에서 확인할 내용 | 우리 서비스가 볼 데이터 |
|-------------------|----------------------------------|-------------------------|
| 원하지 않은 폴더까지 백업된다 | 프로그램 파일 등이 자동 업로드 | 동기화 대상 |
| 다운로드했던 파일을 방치한다 | 오래된 사진·영상·백업 | 마지막 접근일 |
| 파일 버전이 계속 쌓인다 | PowerPoint 등 대형 파일 버전 누적 | 버전 기록 |
| 오래된 백업을 잊어버린다 | 존재 자체를 기억하지 못함 | 생성일·접근일 |

### ④ 중복을 판단하기 어려움

| 사용자 페인포인트 | 실제 사용자 표현에서 확인할 내용 | 우리 서비스가 볼 데이터 |
|-------------------|----------------------------------|-------------------------|
| 이름이 달라 같은 파일인지 모르겠다 | `(1)`, `(2)`, `copy` 등 | 콘텐츠 해시 |
| 이름은 같지만 내용이 다른 파일이 있다 | 파일명만으로 삭제하기 위험 | 해시·수정일 |
| 여러 위치의 사본 중 무엇을 지울지 모르겠다 | 백업인지 불필요한 사본인지 판단 어려움 | 저장 위치·맥락 |
| 버전과 중복을 구별하기 어렵다 | 같은 파일의 과거 버전 문제 | 버전 메타데이터 |

### ⑤ 삭제가 무서움

| 사용자 페인포인트 | 실제 사용자 표현에서 확인할 내용 | 우리 서비스가 볼 데이터 |
|-------------------|----------------------------------|-------------------------|
| 중요한 파일을 지울까 걱정된다 | 삭제 전 불안 | 위험도 |
| 클라우드에서 지우면 PC에서도 사라질까 걱정된다 | 동기화 구조를 이해하기 어려움 | 동기화 관계 |
| 백업인지 중복인지 모르겠다 | 안전을 위해 그냥 둠 | 백업 여부 |
| 어떤 사본을 남겨야 할지 모르겠다 | 삭제 의사결정 부담 | 보존 위치 추천 |

### ⑥ 정리 자체가 귀찮음

| 사용자 페인포인트 | 실제 사용자 표현에서 확인할 내용 | 우리 서비스가 볼 데이터 |
|-------------------|----------------------------------|-------------------------|
| 파일을 하나씩 확인해야 한다 | 수동 정리 부담 | 자동 후보 분류 |
| 여러 서비스를 각각 열어야 한다 | 저장공간별 관리 화면 분리 | 통합 탐색 |
| 용량이 찬 뒤에야 정리한다 | 사후 대응 | 사용량 추세 |
| 그냥 돈 내고 용량을 늘린다 | 정리보다 업그레이드가 쉬움 | 요금제 경계 |

### ⑦ 동기화가 이해하기 어려움

| 사용자 페인포인트 | 실제 사용자 표현에서 확인할 내용 | 우리 서비스가 볼 데이터 |
|-------------------|----------------------------------|-------------------------|
| 동기화와 백업의 차이를 모르겠다 | 삭제 영향에 대한 혼란 | 동기화 상태 |
| 원하지 않는 파일이 자동 업로드된다 | OneDrive 자동 백업 사례 | 동기화 정책 |
| 동기화를 끄면 파일이 어떻게 되는지 모르겠다 | 로컬 파일 손실 우려 | 로컬/클라우드 상태 |
| 기기마다 상태가 달라 혼란스럽다 | PC별 파일 구조 불일치 | 기기간 상태 |

### ⑧ 저장공간 부족이 실제 작업을 방해함

| 사용자 페인포인트 | 실제 사용자 표현에서 확인할 내용 | 우리 서비스가 볼 데이터 |
|-------------------|----------------------------------|-------------------------|
| 파일 업로드가 안 된다 | 용량 한도 도달 | 잔여 용량 |
| 동기화가 멈춘다 | 노트북↔데스크톱 동기화 실패 | 동기화 오류 |
| 문서 저장에 문제가 생긴다 | Office 작업 영향 | 서비스 상태 |
| 계속 용량 부족 알림이 온다 | 반복적인 경고 | 사용률 |

### ⑨ 비용 문제

| 사용자 페인포인트 | 실제 사용자 표현에서 확인할 내용 | 우리 서비스가 볼 데이터 |
|-------------------|----------------------------------|-------------------------|
| 용량 때문에 요금제를 올려야 한다 | 삭제 vs 업그레이드 고민 | 현재 요금제 |
| 더 내기 전에 정리하고 싶다 | 추가 결제 회피 | 정리 가능 GB |
| 어느 정도 지우면 요금제를 낮출 수 있는지 모른다 | 정리의 금전적 효과 불명확 | 요금제 경계 |

### ⑩ 정리 효과가 보이지 않음

| 사용자 페인포인트 | 실제 사용자 표현에서 확인할 내용 | 우리 서비스가 볼 데이터 |
|-------------------|----------------------------------|-------------------------|
| 지우기 전에 얼마나 확보되는지 모르겠다 | 노력 대비 효과 불명확 | 확보 예상 GB |
| 어떤 행동이 가장 효과적인지 모르겠다 | 정리 우선순위 부재 | GB/행동 |
| 계속 다시 쌓인다 | 일회성 Cleaner 한계 | 증가 추세 |

## 5. 해결 — 우리 서비스 (BIUM / Digital Diet)

### 5-1. 포지셔닝

| 기존 Cleaner / 탐색기 | BIUM |
|----------------------|------|
| 폴더를 열어 수동 삭제 | **디지털 집**에서 공간이 한눈에 보임 |
| “전부 삭제” 압박 | **근거(해시·위치·크기)를 보여 주고 사용자가 결정** |
| 로컬만 또는 클라우드만 | Desktop · Laptop · Phone · Cloud · Mail **통합** |
| 삭제가 무섭다 | **하나만 남기기 / 어디에 남길지** 선택 |
| 일회성 청소 | 고양이가 주기적으로 **찾아오는 루틴** |

### 5-2. 핵심 UX 루프 (피피티 데모 흐름)

```
내 디지털 집
  → 고양이가 방을 돌아다님 (Desktop → Laptop → Phone → Cloud)
  → 중복·오래됨·대용량 후보를 발견
  → 사용자에게 가져옴 (비교 근거)
  → 사용자가 결정 (하나만 남기기 / 그대로 두기)
  → 방이 실제로 깨끗해지고, 확보 GB·청결도가 올라감
```

### 5-3. 페인포인트 → 기능 매핑 (요약)

| Pain | BIUM 대응 |
|------|-----------|
| ① 뭐가 찼는지 모름 | 방별·저장소별 점유량 HUD, 용량 순위 |
| ② 흩어짐 | Connected Spaces + 통합 인덱스 |
| ③ 의도치 않은 적재 | 오래된 파일·메일 첨부·버전 후보 |
| ④ 중복 판단 어려움 | 콘텐츠 해시 기반 중복 그룹 |
| ⑤ 삭제 두려움 | 위험도·동기화 맥락·보존 위치 추천 |
| ⑥ 귀찮음 | 고양이 탐색 + 하나씩 확인하기 |
| ⑦ 동기화 혼란 | 위치·동기화 관계를 말로 풀어 제시 |
| ⑧ 작업 방해 | 잔여 용량·정리 가능 GB를 먼저 보여줌 |
| ⑨ 비용 | 요금제 경계·절감 가능액(추정, mock 명시) |
| ⑩ 효과 안 보임 | 확보 GB count-up, 청결도, 정리 기록 |

### 5-4. 하지 않는 것 (신뢰 원칙)

- 확인 없는 **일괄 삭제 / 모두 정리하기** UI 지양  
- 검증되지 않은 **개인 CO₂를 확정 숫자로 제품에 박제하지 않음**  
- “오래된 파일 = 무조건 쓰레기”로 표현하지 않음  
- 추천은 하되, **남길 위치는 사용자가 선택**

## 6. 기대효과 (Closing)

### 사용자

- **시간**: 여러 Drive·탐색기를 열어보지 않아도 후보가 모임  
- **심리**: 삭제 전 비교 근거 → “지워도 되는 이유”가 보임  
- **비용**: 업그레이드 전에 확보 가능한 GB·요금제 경계를 인지  
- **습관**: 용량이 찬 뒤의 응급처치가 아니라, 집 청소 같은 루틴

### 비즈니스·사회 (발표 톤)

- 불필요 복제·방치 저장의 **수요 자체**를 줄이는 방향  
- “용량 업셀”이 아닌 **디지털 다이어트** 카테고리  
- LLM 시대의 그림자 비용(저장·동기화·버전)을 개인이 다룰 수 있는 UX로 번역

### 한 줄 클로징

> LLM이 데이터를 더 만들수록,  
> **방치된 사본을 찾아 정리하는 경험**이 더 필요해진다.  
> BIUM은 그 경험을  
> **게임 같은 디지털 집 + 고양이 에이전트**로 만든다.
